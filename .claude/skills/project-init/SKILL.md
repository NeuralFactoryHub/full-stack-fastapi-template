# Project Init — Auto-generate project.yml

## Overview

Scan the codebase to discover services, infer stacks, detect dependencies, and generate a `.claude/project.yml` configuration file. This file is the single source of truth for how agents understand the project's architecture. The skill also scaffolds a layered, lean CLAUDE.md (root pointers + one file per service).

**Announce at start:** "I'm using the project-init skill to generate project.yml."

## When to Use

- First time setting up Claude Code agents on a project
- After major architectural changes (new services, renamed services)
- When `/project-init` slash command is invoked
- When the orchestrator detects project.yml is missing

## Workflow

### Step 1: Read Project Context

1. Read `CLAUDE.md` at the repo root (if exists) for:
   - Project name, description, language
   - Service listing and descriptions
   - Data flow diagrams
   - Build/lint commands
2. Read `README.md` at the repo root (if exists) for additional context
3. Note the `artifacts_path` — default to `docs/project_context` if not specified

### Step 2: Discover Services

List top-level directories. For each directory, detect the stack:

| Signal | Stack Detection | Suggested Skill |
|--------|----------------|-----------------|
| `requirements.txt` + `app/main.py` with FastAPI import | `python-fastapi` | `backend-python` |
| `package.json` + `next.config.*` (next.config.js/mjs/ts) | `nextjs` | `frontend-nextjs` |
| `package.json` + `tsconfig.json` (no next.config) | `express-ts` | `backend-nextjs` |
| `CLAUDE.md` exists in subdir | Read it for additional context | Infer from content |

For each detected service, also:
- Read `package.json` → `scripts` for `lint_cmd`, `build_cmd`, and `test_cmd`
- Read `CLAUDE.md` in the service directory for documented commands
- If no commands found, leave empty (QA will use stack-based defaults)

Record every command **scoped to the service directory** — never an org-wide
suite. Per-subdirectory lint/build/test commands keep verification fast and
focused (Anthropic large-codebase guidance). `test_cmd` stays empty unless the
service actually has a test suite.

**Monorepo detection:** If the root itself has `package.json` + `next.config.*` (not a subdirectory), treat the root as a single service.

### Step 3: Infer Dependencies

Scan application source files for cross-service calls:

1. **Python services:** Search for `requests.get(`, `requests.post(`, `httpx.`, `fetch(` patterns with URLs containing other service names
2. **TypeScript services:** Search for `fetch(`, `axios.`, HTTP client calls referencing other services
3. **Environment variables:** Read `serverless.yml` or `.env*` files for env vars pointing to other service URLs (e.g., `SEARCH_SERVICE_URL`, `INGESTION_API_URL`)
4. **CLAUDE.md data flow:** Parse any data flow diagrams from the root CLAUDE.md

For each dependency found, record:
- `from`: calling service name
- `to`: target service name
- `protocol`: HTTP, SSE, gRPC, etc.
- `description`: brief description of the interaction

### Step 4: Detect ClickUp Integration

Search for ClickUp configuration:
1. Look for `project.yml` → `integrations.clickup` for project parameters
2. Look for an existing `docs/backlog/.clickup-sync.json` sync-state file
3. Search for `clickup` references in CLAUDE.md or memory files

If found, populate `integrations.clickup` with:
- `enabled: true`
- `workspace_id`, `list_id`, `default_assignee`, `default_status`

### Step 5: Detect Integration Contracts

Search for shared types/enums between services:

1. **Shared enums:** Look for enum definitions that appear in multiple services (e.g., event types, status codes, source types)
2. **API schemas:** Look for matching request/response types across service boundaries
3. **SSE events:** If frontend consumes SSE from backend, the event type enum is a contract

For each contract found, record:
- `name`: contract identifier
- `type`: enum, schema, event-types
- `owner_service`: which service defines it
- `consumer_services`: which services use it
- `description`: what it represents

### Step 6: Generate project.yml

Assemble all discovered information into the project.yml schema:

```yaml
# Auto-generated by project-init skill.
# Last updated: <current ISO timestamp>

project:
  name: "<from CLAUDE.md or repo directory name>"
  description: "<from CLAUDE.md or inferred>"
  language: "<from CLAUDE.md or 'en'>"
  artifacts_path: "docs/project_context"

services:
  - name: "<service-name>"
    path: "<relative-path>/"
    stack: "<detected-stack>"
    skill: "<suggested-skill>"
    lint_cmd: "<detected or empty>"
    build_cmd: "<detected or empty>"
    test_cmd: "<detected or empty — only if the service has a test suite>"

integrations:
  clickup:
    enabled: <true/false>
    workspace_id: "<if found>"
    list_id: "<if found>"
    default_assignee: "<if found>"
    default_status: "planning"

architecture:
  service_dependencies:
    - from: "<service>"
      to: "<service>"
      protocol: "<protocol>"
      description: "<description>"

  integration_contracts:
    - name: "<contract-name>"
      type: "<type>"
      owner_service: "<service>"
      consumer_services: ["<service>"]
      description: "<description>"

onboarding:
  # One-time per-project setup. project-init seeds the LSP rows from the
  # detected stacks; an engineer flips `done` to true once installed.
  lsp:
    - stack: "<detected-stack>"
      language_server: "<recommended server, e.g. pyright / typescript-language-server>"
      done: false
```

### Step 7: Scaffold Layered CLAUDE.md & Codebase Map

The harness expects a **layered, lean** CLAUDE.md (Anthropic large-codebase
guidance): a root file with only pointers, the codebase map, and critical
gotchas, and one CLAUDE.md per service holding that service's local
conventions. Initialize context *in the subdirectories*, not all in the root.

**Per-service CLAUDE.md.** For each service in `services`:

1. If `<service.path>/CLAUDE.md` does **not** exist, scaffold a short one:
   - Stack and the service's role in the system (1–2 lines).
   - **The skill that applies here** — name the `skill` from this service's
     `project.yml` entry explicitly (e.g. "For work in this service, load the
     `backend-python` skill."). This path-scopes skill activation: an agent
     walking the directory tree finds the right skill from the local CLAUDE.md
     instead of guessing.
   - Local conventions an agent must follow (structure, naming, error handling,
     state management).
   - `lint_cmd` / `build_cmd` / `test_cmd` for this service (mirror `project.yml`).
   - Service-specific gotchas.
2. If it already exists, leave it untouched — flag it for the developer to
   review for staleness.

**Root CLAUDE.md + codebase map.** The root `CLAUDE.md` should point to the
service files and hold only cross-cutting gotchas, not duplicate per-service
detail. Ensure it contains a **Codebase map** section: a lightweight list of
the top-level folders with a one-line description each (built from Step 2). On
unconventional layouts this map is what lets an agent orient without guessing.
If the root file has grown long, suggest trimming it.

**Editor setup.** Add (or update) an *Editor setup* section in the root
CLAUDE.md listing the LSP / code-intelligence plugin recommended for each
detected stack (e.g. a Python language server for `python-fastapi`, a
TypeScript language server for `nextjs`). Mirror these into
`project.yml.onboarding.lsp` so the setup is verifiable per project.
Symbol-level navigation beats text grep on large codebases — flag it as a
high-ROI, one-time install, especially for multi-language repos.

Keep every CLAUDE.md short. A stale or bloated CLAUDE.md teaches Claude the
wrong thing. List the files created / flagged in the validation summary below.

### Step 8: Present for Validation

Present the generated configuration to the user in a readable format:

```
Detected services:
  1. <name> (<path>) — stack: <stack>, skill: <skill>
  2. <name> (<path>) — stack: <stack>, skill: <skill>

Dependencies:
  - <from> → <to> (<protocol>)

Contracts:
  - <name> (<type>): <owner> → [<consumers>]

ClickUp: <enabled/disabled>

CLAUDE.md:
  - <service>/CLAUDE.md (created | exists — review for staleness)
  - root CLAUDE.md (ok | suggest trimming)
  - codebase map (present | added)
  - editor setup / LSP (<N> stacks → onboarding.lsp seeded)
```

Ask: "Does this look correct? Any services to add/remove/modify?"

### Step 9: Save

After user approval:
1. Write `.claude/project.yml`
2. Write any service `CLAUDE.md` files approved in Step 7
3. Confirm: "project.yml saved. Agents will now use this configuration."

## Edge Cases

- **Empty repo / no services detected:** Generate a minimal project.yml with just the project name and empty services list. Tell the user to add services manually or re-run after adding code.
- **Single-service repo:** Still generate project.yml — it's useful for lint/build commands and future growth.
- **Skill not found in `.claude/skills/`:** Use the suggested skill name anyway. The user can create it later or use a skill template from `.claude/skill-templates/`.
