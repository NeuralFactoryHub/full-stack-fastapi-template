# ADR-0005: Alembic migrations as the only schema-change mechanism

- **Status:** Accepted
- **Date:** 2026-05-22 (documented retrospectively)
- **Deciders:** Template authors

## Context

The database schema is derived from SQLModel definitions in `app/models.py`.
SQLModel can create tables directly from model metadata
(`SQLModel.metadata.create_all`), which is convenient in development but cannot
*evolve* an existing schema — it neither alters columns nor preserves data, and
leaves no record of what changed.

Staging and production hold real data that must survive schema changes, and
those changes must be reviewable and repeatable across environments.

## Decision

We will make **Alembic migrations the sole mechanism** for schema changes:

- `SQLModel.metadata.create_all` is intentionally left commented out in
  `core/db.py`; tables are created only by migrations.
- Every model change is paired with a migration —
  `alembic revision --autogenerate -m "..."` — that is reviewed and committed
  alongside the model change.
- The `prestart` container runs `alembic upgrade head` on every startup, before
  the backend starts, so each environment converges to the latest schema
  automatically.
- Migrations are generated *inside the running container* so autogenerated
  files land in the mounted `app/` directory.

## Alternatives Considered

| Option | Why not chosen |
|--------|----------------|
| `SQLModel.metadata.create_all` at startup | Cannot alter existing tables or preserve data; no version history; unsafe against a populated database. |
| Hand-written SQL migration scripts | More effort and more error-prone than Alembic autogenerate; no link to the ORM metadata. |
| An external migration tool (e.g. Flyway) | Adds a non-Python tool to a Python stack; Alembic is the native SQLAlchemy/SQLModel choice. |
| Apply migrations manually at deploy time | Error-prone and easy to forget; the `prestart` job makes it automatic and ordered. |

## Consequences

**Positive**

- Schema changes are versioned, reviewable, and reproducible across
  environments.
- `prestart` guarantees the schema is current before the backend serves
  traffic — the backend never runs against an un-migrated database.
- Migration files form an auditable history of the schema's evolution.

**Negative / trade-offs**

- Every model change carries the discipline cost of generating, reviewing, and
  committing a migration.
- Autogenerate is imperfect — it can miss renames or server defaults and emit
  destructive operations — so each script must be read before commit.
- A faulty migration blocks `prestart`, and therefore the backend, on deploy;
  migrations should be kept reversible and tested.

**Follow-ups**

- Keep migrations forward-and-backward safe; verify the `downgrade` path for
  risky changes.
- Consider a CI check that the models and the migration head are consistent
  (no un-migrated model drift).
